Claude Code · Multi-Agent

Build a self-driving
coding pipeline

Tell Claude to implement a GitHub issue. It fetches the issue, plans the work, writes the code in an isolated worktree, reviews it, and opens a PR — without you watching.

How it works

Three concepts you need to understand before writing a single config file.

Concept 1
Main thread = orchestrator
The Claude session you talk to IS the orchestrator. You don't need a separate orchestrator agent. It reads your request, fetches context, and decides which workers to spawn.
Concept 2
Subagents = specialists
Agents in .claude/agents/*.md are workers with a focused job, restricted tools, and their own context window. The orchestrator delegates to them and synthesizes results.
Concept 3
Worktrees = isolation
Add isolation: worktree to an agent and it gets its own clean git checkout. Changes stay isolated from your main branch until you review and merge them.
The key insight: Claude uses each agent's description field to decide when to delegate. Write descriptions that clearly state when to use the agent — Claude picks the right one automatically.

Your 3-agent stack

People who've shipped multi-agent workflows converge on 3 roles. You could add a dedicated QA agent, but the reviewer handles testing and gives you the same coverage with less overhead.

planner

Reads the issue and explores the codebase. Returns a structured implementation plan: files to touch, steps to follow, tests to write. Read-only — never modifies anything.

model: haiku read-only permissionMode: plan
implementer

Takes the planner's output and writes the code. Runs in an isolated git worktree so your main branch is never touched. Commits when done and reports results.

model: sonnet isolation: worktree full tools
reviewer

Reviews the diff, runs the test suite, and gives a clear APPROVE / REQUEST CHANGES / BLOCK verdict. Also the QA layer — surfaces failing tests before the PR is created.

model: sonnet Bash + read-only runs tests
+ optional: researcher

Add this for issues that need external research (docs, RFCs, package APIs). It's a web-search-only agent that hands context to the planner. Skip it initially.

WebSearch only add later
On model choice: Planner uses Haiku — it's read-only codebase exploration, speed matters and cost adds up. Implementer and reviewer both use Sonnet because you want quality there. Don't use Opus for the whole pipeline unless you're debugging something subtle.

File structure

Everything lives inside .claude/ at your project root. Commit it — your whole team gets the same agent behavior. The global commands live in ~/.claude/commands/ and are available across every repo.

your-project/ ├── .claude/ │ ├── agents/ │ │ ├── planner.md # read-only analyst │ │ ├── implementer.md # writes code in worktree │ │ └── reviewer.md # tests + code review │ └── commands/ │ ├── spec.md # /spec — grill an issue into a spec │ └── build.md # /build — full AFK pipeline ├── CLAUDE.md # project rules + agent workflow └── ...your code... # Global commands (across all repos): ~/.claude/commands/ ├── bootstrap.md # /bootstrap — one-shot project setup ├── backlog.md # /backlog — natural language backlog manager └── reformat-backlog.md # /reformat-backlog — normalize any backlog file
Global vs. project commands: /spec and /build are project-level — they're committed to your repo and baked to a specific backend (GitHub, Gitea, or local) at bootstrap time. /backlog, /reformat-backlog, and /bootstrap are global — they live in ~/.claude/commands/ and auto-detect context at runtime.

Agent files

.claude/agents/planner.md 
---
name: planner
description: Analyzes issues and the codebase to produce a structured implementation plan. Use first on any new issue or feature.
tools: Read, Grep, Glob, Bash
model: haiku
effort: high
permissionMode: plan
color: blue
---

You are a senior software architect. Your job is to analyze an
issue and the codebase, then produce a clear implementation plan.

## Process
1. Read the issue thoroughly (provided in the delegation prompt)
2. Use Grep and Glob to explore files related to the issue
3. Read the key files to understand existing patterns
4. Identify what needs to change and why
5. Produce a structured plan (see Output Format below)

## Output Format
Return a plan with these sections:

**Summary** — 2-3 sentences describing the approach

**Files to modify** — List each file with a brief rationale

**New files** — Any new files needed, with their purpose

**Implementation steps** — Numbered, ordered, concrete steps
(reference actual function names and file paths)

**Tests to write** — What tests cover this change

**Risks** — Edge cases, breaking changes, or concerns

## Rules
- Name actual files. Cite line numbers when relevant.
- Don't implement anything. Return only the plan.
- If the issue is unclear, call out what's ambiguous.
- Keep the plan actionable enough that another agent can
  follow it without talking to you again.
.claude/agents/implementer.md 
---
name: implementer
description: Implements features and bug fixes based on a provided plan. Runs in an isolated git worktree. Use after planner has returned a plan.
tools: Read, Edit, Write, Bash, Grep, Glob
model: sonnet
effort: medium
permissionMode: acceptEdits
isolation: worktree
color: green
---

You are a senior software engineer implementing features based on
a plan provided by the orchestrator.

## Process
1. Read the implementation plan carefully
2. Explore the files mentioned in the plan before editing
3. Implement each step methodically
4. Write tests as specified in the plan
5. Run the tests: [TEST_COMMAND]
6. Run the linter: [LINT_COMMAND]
7. Stage all changes and create a commit

## Standards
- Match the existing code style exactly (indentation, naming, patterns)
- Write tests before or alongside the implementation
- Keep changes focused — don't refactor unrelated code
- If you discover the plan is wrong, note the deviation and explain why
- Use conventional commit format: `feat: ...` or `fix: ...`

## Commit message format
```
feat(scope): short description

- Bullet points for key changes
- Reference issue number if known

Closes #<issue-number>
```

## When Done — Report
- What was implemented (brief)
- Test results (pass/fail counts)
- Any deviations from the plan and why
- The commit hash
.claude/agents/reviewer.md 
---
name: reviewer
description: Reviews code changes for correctness, quality, and test coverage. Runs the test suite and gives a clear verdict. Use after implementer completes work.
tools: Read, Bash, Grep, Glob
model: sonnet
effort: high
color: orange
---

You are a skeptical senior code reviewer. Review the implementation
and give a clear, actionable verdict. Do not soften verdicts.

## Process
1. Run `git diff main` (or the appropriate base branch)
2. Read each modified file in full context
3. Run the test suite: [TEST_COMMAND]
4. Run the linter: [LINT_COMMAND]
5. Check that new code has test coverage

## Review Checklist
- Logic correctness and edge cases
- Tests pass and cover new/changed code
- No security issues (injection, secrets in code, unvalidated input)
- No breaking changes to public APIs
- Code follows project conventions (naming, structure, patterns)
- No debugging artifacts (console.logs, TODO comments, dead code)
- Error handling is appropriate

## Verdict Format

Start your response with one of:

**✅ APPROVE** — Implementation is solid, create the PR
**⚠️ REQUEST CHANGES** — Issues found but fixable, list them
**🚫 BLOCK** — Fundamental problem, needs replanning

Then provide:
- Issues found (label: critical / warning / nit)
- Test results (pass/fail/skip counts)
- What's done well

Be direct. If this would pass your real code review, say so.
.claude/commands/build.md (GitHub variant) 
Implement GitHub issue #$ARGUMENTS end-to-end.

## Pre-flight
Run: `gh issue view $ARGUMENTS --json labels`
Check that the issue has the `agent-ready` label.
If it does NOT have `agent-ready`, stop immediately and tell the user
to run `/spec $ARGUMENTS` first.

## Step 1 — Fetch context
Run: `gh issue view $ARGUMENTS --json title,body,labels,comments`

## Step 2 — Plan
Delegate to the `planner` agent.
Pass: the full issue text + project context from CLAUDE.md.
Wait for the structured implementation plan.

## Step 3 — Implement
Delegate to the `implementer` agent.
Pass: the planner's full output.
It will implement in an isolated worktree and commit when done.
Wait for its report (commit hash, test results, deviations).

## Step 4 — Review
Delegate to the `reviewer` agent.
Pass: the implementer's commit hash and summary.
Wait for its APPROVE / REQUEST CHANGES / BLOCK verdict.

## Step 5 — Verdict

If **✅ APPROVE**:
  Run `gh pr create --fill` and report the PR URL.
  Run `gh issue edit $ARGUMENTS --add-label "in-review"`

If **⚠️ REQUEST CHANGES**:
  Surface the reviewer's feedback in full.
  Ask the user how to proceed before doing anything else.

If **🚫 BLOCK**:
  Share the reviewer's concerns and stop.
  Do not attempt a fix — this needs replanning via `/spec`.

## Agent Pipeline

When working on an issue, always follow this sequence:
1. Fetch the issue (gh issue view / curl Gitea API / read BACKLOG.md)
2. Delegate to `planner` — analysis and plan, read-only
3. Delegate to `implementer` — code in isolated worktree
4. Delegate to `reviewer` — tests + verdict
5. If APPROVE: create PR. If REQUEST CHANGES: surface to user.

Issue spec

The pipeline assumes issues are well-specified. Raw ideas aren't. Run /spec first — interactively, with you in the loop — before tagging anything agent-ready.

The problem
Vague input → broken output
If the issue says "add dark mode" and nothing else, the planner guesses, the implementer builds the wrong thing, and the reviewer approves it. Garbage in, garbage out — politely and expensively.
The fix
A label-based quality gate
Only issues tagged agent-ready get picked up by /build. You earn that label by running /spec, which interrogates the idea until it's specific enough to build from.
Inspired by Matt Pocock's grilling technique: The spec prompt doesn't help you flesh out the idea — it interrogates it. It asks the questions your PR reviewer will ask, before any code is written. You stay in the loop; this step is intentionally interactive.

The /spec slash command

Lives in .claude/commands/spec.md (project-level, written by bootstrap). Type /spec 47 — Claude fetches the issue and grills you on it. When you're satisfied, it rewrites the issue body and applies the agent-ready label.

.claude/commands/spec.md (GitHub variant) 
Refine issue #$ARGUMENTS into a spec that an agent can implement
without asking clarifying questions.

## Step 1 — Fetch the raw issue

Run: `gh issue view $ARGUMENTS --json title,body,labels,comments`

Read it carefully. Don't tell me what it says yet.

## Step 2 — Grill me

Your goal: reach a point where you could hand this issue to another
engineer — one who has never spoken to us — and they would know
exactly what to build, what done looks like, and what not to touch.

Ask me questions until you're there. Ask ONE question at a time and
wait for my answer before asking the next. Follow threads — if my
answer opens a new gap, chase it before moving on.

Don't be gentle. You're a senior engineer who has been burned by
vague tickets. You've seen "add dark mode" become a three-month
nightmare. You know that words like "improve", "better", "simple",
and "clean up" are hiding decisions that someone has to make.

Areas to probe as needed — not a checklist, but a lens:
- What specifically is broken or missing today?
- What does a user do or see when this is done that they can't now?
- What is explicitly out of scope?
- What breaks if the implementation goes slightly wrong?
- What must not change — existing APIs, patterns, files, behavior?
- What assumptions is the issue author making that aren't written down?

Keep asking until you're confident. There's no fixed number of
questions. Some issues need two; some need twelve.

## Step 3 — Write the refined spec

When you have what you need, produce a rewritten issue body in this
exact format — no other sections, no extra headers:

```
## Problem
[1–2 sentences. Specific. No weasel words.]

## Acceptance Criteria
- [ ] [Testable. A reviewer can verify this without asking anyone.]
- [ ] [Add as many as the issue actually needs.]

## Out of Scope
- [Explicit exclusion — something someone might assume is included]

## Edge Cases
- [Scenario]: [Expected behavior]

## Technical Notes
[Constraints, affected files, patterns to follow, or compatibility
requirements. Omit this section entirely if there are none.]
```

Show me the draft. Ask: "Does this capture it? Anything to change?"

Iterate until I'm satisfied. Then run:
  `gh issue edit $ARGUMENTS --body "[the final spec]"`
  `gh issue edit $ARGUMENTS --add-label "agent-ready"`

Confirm when done. The issue is now ready for `/build $ARGUMENTS`.
Tip: Create the agent-ready label first: gh label create "agent-ready" --color "#3fb950" --description "Spec is complete — safe for agent pipeline". Bootstrap does this for you.

The workflow in practice

1
Idea lands in your tracker
You open an issue (or add to BACKLOG.md) with a rough idea. No label. It's just a note for now.
2
You run /spec <id>
Interactive session. Claude grills you, you answer. Takes 5–10 minutes. Claude rewrites the issue body and adds the agent-ready label when you're satisfied.
3
Run /build <id> and walk away
The pipeline now has everything it needs. Planner reads a tight spec, implementer has clear acceptance criteria, reviewer knows what done looks like.

The AFK workflow

What actually happens when you type /build 47 and go make coffee.

1
You kick it off
Type /build 47 in Claude Code. The slash command file loads, replacing $ARGUMENTS with 47. Claude reads the instructions and starts.
2
Pre-flight check
Claude checks for the agent-ready label. If it's missing, it stops and tells you to run /spec 47 first. No label, no pipeline.
3
Orchestrator fetches context
Main Claude fetches the full issue. It reads your CLAUDE.md to understand the project, then prepares the delegation prompt for the planner.
4
Planner agent runs (Haiku, read-only)
Gets its own fresh context window. Grep/Globs through the codebase, reads relevant files. Returns a structured plan: files, steps, tests, risks. Runs cheap and fast.
5
Implementer runs in isolated worktree (Sonnet)
Claude Code creates a temporary git worktree — a clean checkout branched from your default branch. The implementer works there. Your main checkout is completely untouched. It writes code, runs tests, commits.
6
Reviewer checks the diff (Sonnet)
Reads the full diff, runs the test suite, checks coverage. Returns a verdict. If APPROVE, Claude creates the PR. If REQUEST CHANGES, it surfaces the feedback and asks you how to proceed.
7
PR created, you get the link
Claude runs gh pr create --fill using the commit messages. Reports the PR URL. You review it like any other PR — you're the final human gate.
For true AFK mode: Run Claude Code with claude --permission-mode auto or set permissionMode: dontAsk on your agents. Auto mode uses a background classifier to approve routine operations. You'll still get surfaced for anything unusual.

Permission mode cheat sheet

permissionMode options
plan        # Read-only. Can't write or run commands. Good for planner.
acceptEdits # Auto-approves file edits. Prompts for bash. Good for implementer.
auto        # Background classifier approves routine ops. Best for AFK.
dontAsk    # Auto-denies permission prompts. Aggressive; use with care.
default     # Manual mode. Prompts you for everything. Safe default.

Bootstrap: one-shot setup

Run /bootstrap once in a new repo and it writes everything: all three agents, both project commands, and a CLAUDE.md. It auto-detects your backend and substitutes the right tools throughout.

GitHub repos
gh CLI
Detects github.com in your git remote. Uses gh issue view, gh issue edit, gh pr create. Creates the agent-ready label automatically.
Gitea repos
curl + API
Detects any other hostname. Uses the Gitea REST API with your token ($GITEA_TOKEN → config file → .gitea-token in repo root).
No remote
Local BACKLOG.md
No git remote found. Issues live in BACKLOG.md at the project root. /spec edits it directly. /build marks items done instead of creating a PR.

What bootstrap does

1
Pre-flight
Verifies you're in a git repo. Reads your remote URL to pick the backend (GitHub / Gitea / local). Stops and explains if something is off.
2
Inspect the project
Detects language, test command, lint command, and source directory. These get substituted into the agent files so [TEST_COMMAND] becomes npm test (or whatever applies).
3
Check for existing files
Scans for .claude/agents/*.md and .claude/commands/*.md. Asks before overwriting — never silently clobbers your existing setup.
4
Write agent files
Creates planner.md, implementer.md, and reviewer.md in .claude/agents/ with detected test/lint commands substituted in.
5
Write command files
Creates spec.md and build.md in .claude/commands/, baked to the detected backend. No runtime detection — these know exactly which API to call.
6
Write or merge CLAUDE.md
If no CLAUDE.md exists, writes the template. If one already exists, reads it, adds only missing sections, shows you the diff before writing. Never removes existing content.
7
Ensure global commands
Checks ~/.claude/commands/ for backlog.md and reformat-backlog.md. Writes them if missing, skips them if already present. Never overwrites global commands you've customized.
8
Create labels / scaffold backlog
GitHub/Gitea: creates agent-ready, in-progress, and in-review labels. Local: scaffolds an empty BACKLOG.md with the canonical structure.
Two things bootstrap can't do for you: Fill in CLAUDE.md's project description and conventions section (only you know those), and add your first issues or backlog items (it can scaffold the structure, but not the content).

Backlog management

The /backlog command is a natural-language interface to your issue tracker — whether that's GitHub, Gitea, or a local markdown file. Tell it what you want; it figures out the rest.

Auto-detection: /backlog reads your git remote -v at runtime and picks the right backend automatically — same logic as bootstrap, but decided fresh each time. Use it from any repo.

Quick capture — the default behavior

Adding an item is frictionless by design. Title only is enough. Everything else can be filled in later with /spec.

Example session

You: add 'dark mode support' to the icebox
Claude: Added ID:#007 · Seq:3 in Icebox.

# Show a summary
You: show the backlog
Claude: [compact summary — IDs, titles, priority, status per section]

BACKLOG.md format

The canonical format for local repos. IDs are permanent and never renumbered. Seq is position within its section and updates when items move.

# Project Name · Backlog <!-- format: v1 | updated: 2026-10-09 --> ## Milestone M1 — Launch > **Goal**: Ship the MVP to beta users > **Target**: 2026-11-01 > **Status**: in-progress ### ID:#001 · Implement JWT refresh tokens `P1` `Seq:1` `in-progress` `agent-ready` **Problem**: Sessions expire after 1hr with no silent refresh... **Acceptance Criteria** - [ ] Silent refresh fires when token is within 5min of expiry - [ ] Expired refresh token redirects to login **Out of Scope**: OAuth flows, remember-me persistence **Edge Cases**: Network offline during refresh: queue and retry **Technical Notes**: Modify `src/auth/token.ts` **Depends on**: none --- ## Backlog > Ungrouped work — no milestone assigned yet ### ID:#004 · Add CSV export to reports `P2` `Seq:1` `todo` **Problem**: Finance team needs report data in Excel. (no spec yet — add with /spec 4) --- ## Icebox > Low priority / no milestone assigned ## Done - [x] ID:#000 Initial project scaffold — 2026-09-15
ID vs Seq: IDs are permanent — they're what you reference in commits (Closes #001) and Depends on fields. Seq is just position in the file. Moving an item changes its Seq; its ID never changes.

Reformatting an existing backlog

Already have a TODO.md or BACKLOG.md in a different format? /reformat-backlog normalizes it into the canonical structure.

Usage
# Auto-find a backlog in the current repo
/reformat-backlog

# Point at a specific file (any name, any format)
/reformat-backlog path/to/my-todo-list.md

The command analyzes your existing file, assigns IDs to items that don't have them, maps section names to canonical ones (In Progress → Backlog + in-progress label, Someday/Maybe → Icebox), normalizes priority tags, and writes the result. If the source file isn't named BACKLOG.md, it asks whether to save as BACKLOG.md, overwrite the original, or specify a path. It never auto-deletes your source file.

Sandcastle: the Docker upgrade

When worktree isolation isn't enough — you want agents that genuinely can't touch your host machine. Matt Pocock's Sandcastle library runs Claude Code inside Docker containers with bind-mounted worktrees.

What it does
Full container isolation

Each agent run gets a Docker container. It can only see the mounted worktree — no access to your filesystem, credentials, or network beyond what you allow. The container is destroyed when the agent finishes.

The pattern
Parallelize AFK agents

Call sandcastle.run() with a task and a branch name. Sandcastle spins up the container, runs the agent, merges the commits back into your repo. Run multiple calls concurrently for parallel implementations.

Getting started

Terminal 
# Install Sandcastle
npm install @ai-hero/sandcastle

# Scaffold the .sandcastle/ config directory + Docker image
npx sandcastle init .

# Build the Docker image (do this once, rebuild after Dockerfile changes)
npx sandcastle docker build-image

Example: sequential reviewer pipeline

Use the sequential-reviewer template as a starting point — it maps almost exactly to the planner → implementer → reviewer pattern.

.sandcastle/main.ts 
import { run } from "@ai-hero/sandcastle";

// Step 1: Implement in an isolated container
const implResult = await run({
  agent: "claude-code",
  branch: `feature/issue-${issueNumber}`,
  prompt: `
    Implement issue #${issueNumber}.
    Use the planner agent, then the implementer agent.
    Commit when done.
  `,
  model: "claude-sonnet-5-5",
});

// Step 2: Review in a separate container (read-only)
const reviewResult = await run({
  agent: "claude-code",
  branch: implResult.branch,
  prompt: `
    Review the changes on branch ${implResult.branch}.
    Run the test suite. Give an APPROVE or REQUEST CHANGES verdict.
  `,
  model: "claude-sonnet-5-5",
});

console.log(reviewResult.output);
Prerequisites: Docker Desktop and Git must be installed. Set ANTHROPIC_API_KEY in .sandcastle/.env. Note that Sandcastle uses API credits directly — not your Max subscription.

Phase your adoption

  • Now: Run /bootstrap in your repo. Use /backlog to add and manage issues, /spec to grill them into specs, then /build with you approving prompts. Build trust in the pipeline.
  • Soon: Switch implementer to permissionMode: auto for the true AFK experience within your existing checkout.
  • Later: Add Sandcastle when you want full container isolation and true parallel agents. Use the sequential-reviewer template as your starting scaffold.
